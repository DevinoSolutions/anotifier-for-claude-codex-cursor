# Remote Approval: Approve or Deny Agent Permission Requests from the Phone

**Date:** 2026-10-08
**Status:** Proposed. Security design only; no code. Nothing here is approved to ship.
**Scope:** Claude Code and Codex CLI `PermissionRequest` hooks answered through ntfy action buttons. Cursor and Gemini CLI are out of scope (see [Non-goals](#non-goals)).

## Overview

When an agent is about to ask for permission (run a shell command, edit a file, call an MCP tool), an opt-in anotifier hook publishes an ntfy notification with **Approve** and **Deny** buttons. The hook then waits on a private response channel and hands the decision back to the agent on stdout. If no valid answer arrives in time, the hook returns *no decision* and the agent shows its normal terminal prompt.

This turns an ntfy channel into a **credential that can execute commands on the user's machine**. Everything below follows from that sentence.

The [2026-07-09 demand record](../research/2026-07-09-feature-demand.md#10-phone-allowdeny-buttons-on-notifications--do-not-build-as-designed) (finding #10) rejected this feature "as designed" for two reasons: hooks must never block the agent, and the project has no server. Both still apply. This design keeps the no-server posture (ntfy relays both directions; the hook is the only verifier) and treats blocking as a deliberate, opt-in exception confined to a separate entry point. It does not pretend the blocking cost away; see [UX: when the hook is allowed to block](#41-when-the-hook-is-allowed-to-block).

### Summary of the recommendation

| Area | Recommendation |
|---|---|
| Response authentication | Per-request, per-decision 128-bit one-time tokens generated by the waiting hook process and held only in its memory. No long-lived HMAC key. |
| Topics | One request topic per install (192-bit name), separate from the existing notification topic. One fresh response topic per request (128-bit suffix). |
| Response authentication caveat | **Anyone who can read the request topic can approve**, because the tokens travel inside the request. Everything else in this table limits who that is. |
| Server | Self-hosted ntfy with `auth-default-access: deny-all` and the ACL recipe below is the recommended setup. Anonymous public ntfy.sh is **not supported in v1** (decision D1). |
| Expiry | Hook waits `waitSeconds` (default 300) and stops listening. Late taps are inert by construction. |
| Failure | Every error, timeout, or malformed reply returns **no decision** (exit 0, `{}`), never `allow`. The agent then prompts at the terminal. |
| Engagement | Only while the user has turned on "away" mode (`anotifier away 2h`) **(default)**, because Codex shows its own approval prompt only after the hook returns. An opt-in `engage: "always"` exists (section 4.1, D5). |
| Eligible tools | `Bash` only by default. File writes (Edit, Write, NotebookEdit, apply_patch) are opt-in because the phone shows only the path, so a file approval is **blind**. A built-in path denylist (agent config, git hooks, shell rc files, CI workflows, `package.json`, ...) always falls back to the terminal (section 4.3). |
| Display | Tool, project, relative path or command summary; secrets scrubbed heuristically; newlines, control, bidi and zero-width characters shown as visible markers; no file contents; Approve withheld when the command does not fit. |
| Concurrency | At most 5 pending approvals per install, enforced with exclusive-create slot files that hold only a PID and an expiry time, never topics or tokens (section 2.3). |
| "Always allow this session" | Not in v1. If built later: Claude only, exact-match rule, `destination: "session"`, never `setMode`. |

## 1. Threat model

### 1.1 Assets

1. **The ability to approve a tool call.** An `allow` decision runs arbitrary shell commands as the user (Bash), writes arbitrary files (Edit/Write/apply_patch), or calls MCP tools with side effects. This is remote code execution on the developer's machine. A file write is code execution too when it lands in a file something else executes (agent hook config, git hooks, shell rc files, CI workflows, `package.json` scripts).
2. **Request content.** Commands, file paths, URLs, MCP arguments, project names. These can contain secrets (`export AWS_SECRET_ACCESS_KEY=...`, `curl -H "Authorization: Bearer ..."`), customer names, and internal hostnames.
3. **Availability of the agent.** A blocked hook stalls the session.

### 1.2 Trust boundaries

```
 dev machine                     ntfy server                 push relay           phone
+---------------------+   TLS   +-------------------+       +-------------+     +-----------+
| agent -> hook       | ------> | request topic     | ----> | FCM / APNs  | --> | ntfy app  |
| (approve.mjs)       |         | (cache 12h)       |       | (ntfy.sh    |     | buttons   |
|   waits on          | <------ | response topic    | <------------------------ | http POST |
|   response topic    |   TLS   |                   |              TLS         |           |
+---------------------+         +-------------------+                           +-----------+
```

- **The ntfy server operator is fully trusted.** It sees every request and every token, and could forge a response. On public ntfy.sh that operator is a third party.
- **On public ntfy.sh, Google FCM and Apple APNs also see request content.** For a topic that anonymous users can read, ntfy.sh forwards the whole message to Firebase, actions included (`data["actions"]`); only topics that deny anonymous read are reduced to a content-free `poll_request` ([server_firebase.go, `toFirebaseMessage`](https://github.com/binwiederhier/ntfy/blob/main/server/server_firebase.go)). The action button bodies, which carry the one-time tokens, therefore transit Google or Apple. The `X-Firebase: no` publish header avoids this ([docs](https://docs.ntfy.sh/publish/#disable-firebase)), at the cost of delivery depending on the app's own connection.
- **ntfy has no end-to-end encryption.** The feature request has been open since 2021 ([binwiederhier/ntfy#69](https://github.com/binwiederhier/ntfy/issues/69), still open on 2026-10-08). Nothing in this design may assume message confidentiality from the server.
- **The phone's stock ntfy app cannot compute anything.** An `http` action sends a fixed method, URL, headers and body chosen by the publisher ([docs](https://docs.ntfy.sh/publish/#send-http-request)). So any "signature" on the response must be precomputed by the hook and shipped inside the request. This is why section 2 uses one-time tokens rather than a phone-side HMAC.

### 1.4 What this design cannot protect against

- A malicious or compromised ntfy server operator.
- Anyone who can read the request topic (by design, they hold the approve tokens).
- A user who approves a malicious command they could read. Remote approval is no safer than the terminal prompt, and the small screen makes it somewhat less safe.

## 2. Mechanism

### 2.1 Components

- `src/approve.mjs`: a new hook entry point, separate from `src/notify.mjs`. It is the only place that can print a decision. `notify.mjs` keeps its never-block contract unchanged.
- `~/.anotifier/approval.json` (mode 0600): server URL, request topic, response topic prefix, optional agent access token. Kept out of `config.json` so that `config.json` can stay shareable and its current permissions are not a factor.
- `~/.anotifier/approvals/` (mode 0700): the pending-slot files of section 2.3 and the away-state file of section 4.1. Neither holds a topic, token or request content.
- `anotifier approval setup | status | off` and `anotifier away [duration|off]` CLI commands.
- A `doctor` check `approval-token` that warns before the agent access token expires (section 2.5).

### 2.2 Topics

| Topic | Name | Lifetime | Who writes | Who reads |
|---|---|---|---|---|
| Request | `anr-` + 32 chars base64url from `crypto.randomBytes(24)` (192 bits), 36 chars | Per install, rotatable | Hook (agent user) | Phone |
| Response | `<responsePrefix>_` + 22 chars base64url from `crypto.randomBytes(16)` (128 bits), where `responsePrefix` is `ans-` + 16 random chars | Per request | Phone (anonymous write-only, see ACL) | Hook |

ntfy topic names allow `[-_A-Za-z0-9]` up to 64 characters ([docs](https://docs.ntfy.sh/publish/#picking-a-topic)); base64url fits that alphabet. The existing notification topic is 16 chars of a 36-letter alphabet, about 82 bits (`cli/setup.mjs:46-53`). It is fine for notifications but is printed by `status`, `doctor` and `setup`, so it must not double as the approval topic.

### 2.3 One request, end to end

1. Agent invokes `approve.mjs` with the `PermissionRequest` JSON on stdin.
2. Gate checks, in order. Any failure prints `{}` and exits 0 within milliseconds:
   approval enabled; away mode active (section 4.1); not snoozed or in quiet hours; tool eligible and no path on the denylist (section 4.3); a free pending slot; `approval.json` readable and server is `https://` (or loopback).

   **Pending slots (the cross-process cap).** Each hook is a separate process, so the cap of 5 needs shared state. The hook claims a slot by exclusive-creating `~/.anotifier/approvals/slot-<n>` for the first free `n` in 0 to 4 (`fs.openSync(path, 'wx')`, the same primitive as `acquireNotifyLock` in `src/notify.mjs`). The file holds only `<pid> <expiresAt>`. Before trying, the hook deletes slot files whose `expiresAt` is in the past or whose PID is no longer alive. It deletes its own slot on every exit path. If no slot is free, or the directory cannot be used at all, the hook returns no decision. That is fail-closed for remote approval and fail-safe for the user, who gets the terminal prompt.
3. Generate `rid` (128 bits), `tAllow` and `tDeny` (128 bits each), response topic, and `expiresAt = now + waitSeconds`.
4. **Subscribe first**: open `GET <server>/<responseTopic>/json` (streaming; [subscribe API](https://docs.ntfy.sh/subscribe/api/)). Subscribing before publishing removes the publish/subscribe race without needing `since=`.
5. Publish the request as JSON to `<server>/` ([publish as JSON](https://docs.ntfy.sh/publish/#publish-as-json)):

   ```json
   {
     "topic": "anr-<192-bit>",
     "title": "my-app · Claude Code wants to run Bash",
     "message": "npm test -- --watch=false\n\nSession 3f2a · expires 14:32",
     "priority": 4,
     "tags": ["lock"],
     "sequence_id": "<rid>",
     "actions": [
       { "action": "http", "label": "Approve", "url": "https://ntfy.example.com/<responsePrefix>_<rid>",
         "method": "POST", "body": "{\"v\":1,\"rid\":\"<rid>\",\"d\":\"allow\",\"t\":\"<tAllow>\"}", "clear": true },
       { "action": "http", "label": "Deny", "url": "https://ntfy.example.com/<responsePrefix>_<rid>",
         "method": "POST", "body": "{\"v\":1,\"rid\":\"<rid>\",\"d\":\"deny\",\"t\":\"<tDeny>\"}", "clear": true }
     ]
   }
   ```

   `sequence_id` lets the hook later replace or clear this notification by publishing again with the same ID ([docs](https://docs.ntfy.sh/publish/#updating-deleting-notifications); the JSON publish field is listed in the [JSON parameters](https://docs.ntfy.sh/publish/#publish-as-json)). ntfy allows at most three actions ([docs](https://docs.ntfy.sh/publish/#defining-actions)).
6. Read the response stream. Each line is a JSON event; the stream also carries `open` and `keepalive` events ([subscribe API](https://docs.ntfy.sh/subscribe/api/)). Keep only `event === "message"`, then parse the response JSON from that event's `message` field. Require `v === 1`, `rid` match, `d` in {`allow`, `deny`}, token equal to that decision's token via `crypto.timingSafeEqual`, and `now < expiresAt`. Ignore anything else. Stop after the first valid message, after 50 messages, after 64 KB, or at expiry.
7. Print the decision (section 3), close the stream, free the slot, publish a receipt ("Allow decision sent" / "Deny decision sent") or an expiry update with the same sequence ID, exit 0. The receipt says what the hook returned, not that the tool ran.

The hook keeps the current request's tokens and topic names only in memory. The only thing it writes to disk is its slot file (a PID and an expiry time), so there is no secret to steal after the process exits.

### 2.4 Why one-time tokens, not an HMAC-signed response

The brief asked for either a per-request nonce with an HMAC-signed response or a one-time token in the action. With the stock ntfy app the phone cannot sign anything; it replays a body the hook wrote. An HMAC over `(rid, decision, expiry)` with a long-lived install key would therefore also be precomputed and shipped inside the request, which makes it a token with structure. What each option buys:

| | One-time random tokens (recommended) | HMAC(installKey, rid ‖ decision ‖ expiry) |
|---|---|---|
| Forgery by someone without the request | Infeasible (128-bit) | Infeasible |
| Forgery by someone who reads the request | Possible | Possible (MAC is in the request) |
| Verifier needs state | Yes, but the verifier is the same process that published | No |
| Long-lived secret on disk | None | `installKey`; if stolen, attacker can mint approvals for any future `rid` they observe |
| Expiry binding | In the hook's memory | Inside the MAC |

HMAC only helps if a different process verifies than publishes, for example a future always-on local daemon. Revisit it then.

Tokens go in the **body**, not the URL. URL query strings land in reverse-proxy access logs; bodies usually do not.

### 2.5 Server options and honest behavior of each

**A. Self-hosted ntfy with ACLs (recommended).** Server config ([access control](https://docs.ntfy.sh/config/#access-control), [ACL](https://docs.ntfy.sh/config/#access-control-list-acl), [tokens](https://docs.ntfy.sh/config/#access-tokens)):

```yaml
auth-file: /var/lib/ntfy/user.db
auth-default-access: deny-all
```

```
ntfy user add agent            # used by the hook
ntfy user add phone            # used by the phone app login
ntfy access agent    anr-<req>         write-only
ntfy access phone    anr-<req>         read-only
ntfy access everyone "<responsePrefix>_*"  write-only
ntfy access agent    "<responsePrefix>_*"  read-only
ntfy token add --expires=90d --label=anotifier agent
```

`<responsePrefix>` is the full `ans-` + 16 chars value from section 2.2, so the pattern reads like `ans-Xy3...Q_*`.

**Token expiry.** When the 90-day agent token expires, every publish fails with an auth error and every approval falls back to the terminal prompt without telling the user why. Setup records the token's expiry date in `approval.json`. A `doctor` check (`approval-token`) warns 14 days before expiry and fails after it. If the server is reachable, the check can confirm the date with the account endpoint the ntfy web app uses (`GET /v1/account`, which lists the user's tokens; **verify the response shape**). The hook also records the last failure class (`auth`, `network`, `quota`) without content, so `status` can name the cause.

Rationale for `everyone` write-only on the response pattern: the `http` action would otherwise need an `Authorization` header, which would be embedded in every request message. ntfy access tokens "grant users full access to the user account" ([docs](https://docs.ntfy.sh/config/#access-tokens)), so embedding one is worse than relying on the 128-bit response topic name plus the token in the body. Anonymous users can write blindly to a response topic but can read nothing.

Properties: only the phone user can read requests (T1, T7 closed for outsiders); only the agent can publish requests (T10 closed); the operator is the user. The server's hostname becomes part of the trust base: DNS hijack, an expired domain, or a dangling record that allows subdomain takeover gives an attacker a server the hook and phone will trust (T8). iOS needs the server's `upstream-base-url` for instant delivery, which forwards only a content-free poll request to ntfy.sh ([docs](https://docs.ntfy.sh/config/#ios-instant-notifications)).

**B. ntfy.sh with an account and a reserved topic.** Reservations need a paid tier (Supporter: 3 reservations; free: 0, per [ntfy.sh/v1/tiers](https://ntfy.sh/v1/tiers)). Only the **request** topic needs a reservation. A reserved request topic that denies anonymous read stops content forwarding to FCM/APNs and stops strangers reading or publishing to it. Response topics stay ordinary anonymous topics with fresh 128-bit names. They need no reservation and no wildcard pattern, which ntfy.sh reservations may not support anyway. Their protection is the unguessable name plus the body token. Which anonymous-access settings ntfy.sh offers on a reserved topic, and whether "no anonymous read or write" is one of them, is **unverified (U8)**. The ntfy.sh operator still sees everything.

**C. Public ntfy.sh, anonymous (zero-infra). Not supported in v1 (D1).** Security reduces to the secrecy of a 192-bit topic name that lives in the config file, the phone app's subscription list, ntfy.sh's 12-hour cache and, unless `X-Firebase: no` is set, Google's or Apple's push infrastructure. Guessing is infeasible; leakage is not. The 250 messages per day per IP limit is shared with all other notifications, and this repo's CI has already hit the ntfy.sh daily quota in E2E runs. Anyone who learns the topic can also publish fake prompts whose buttons fire arbitrary requests from the phone (T10). This is the same model as the prior art and as any "secret link" capability. The recommendation is not to support it in v1 (D1). If it is ever allowed, it requires an explicit acknowledgement, `minimal` display, and `X-Firebase: no` on every request.

### 2.6 Expiry window

- `waitSeconds` default **300** (range 30 to 3600). A long wait is acceptable because it only applies in away mode; the agent was going to wait for the user anyway. The approval window is the exposure window, so it should not be longer than needed.
- The hook's own deadline is `waitSeconds`; the agent's hook `timeout` is set to `waitSeconds + 30` so the hook always exits cleanly first. Claude Code and Codex both default command hooks to 600 s ([Claude](https://code.claude.com/docs/en/hooks#common-fields), [Codex](https://developers.openai.com/codex/hooks)); anotifier's existing entries use 10 s (`setup/patch-config.mjs:244`), so the approval entry needs its own value.
- After expiry nothing listens on the response topic. Stale approvals cannot act (T4).

### 2.7 On timeout or any failure: fall back to the terminal prompt, never allow

Every non-success path prints `{}` and exits 0. That is "no decision" for both agents:

- Claude Code: a hook output without a `decision` object leaves the permission flow unchanged, and a hook killed at its timeout has its output discarded, so the user sees the normal dialog ([docs](https://code.claude.com/docs/en/hooks#exit-code-2-behavior-per-event)). In non-interactive sessions (background subagents, `-p`), "if no hook returns a decision, it denies the tool call" ([docs](https://code.claude.com/docs/en/hooks#permissionrequest)). That is a safe default.
- Codex: "If no matching hook decides, Codex uses the normal approval flow" ([docs](https://developers.openai.com/codex/hooks#permissionrequest)). A timed-out hook is recorded with `error: "hook timed out after Ns"` and no decision ([command_runner.rs](https://github.com/openai/codex/blob/main/codex-rs/hooks/src/engine/command_runner.rs), [permission_request.rs](https://github.com/openai/codex/blob/main/codex-rs/hooks/src/events/permission_request.rs)).

The hook never exits 2. Claude ignores exit 2 for this event, but Codex treats exit 2 with stderr text as a **deny** (`permission_request.rs`, `Some(2)` branch). A stray exit 2 would make the two agents disagree.

The prior art returns `{"behavior": "ask"}` on failure. `ask` is not a documented `behavior` value for `PermissionRequest` in either agent (Claude: `allow`/`deny`; Codex schema enum: `allow`, `deny`). Do not copy it.

### 2.8 Exactly what is shown on the phone

Title: `<project> · <Agent> wants to <verb> <Tool>` (project is the cwd basename, already sent by today's notifications). Body: one content line, then `Session <4-char tag> · expires HH:MM`.

Display mode `summary` is the default. `minimal` and `full` are opt-in. `minimal` shows no command, so a Bash request in `minimal` mode carries no Approve button: only Deny and "At terminal" are offered, because the user cannot judge what would run.

| Tool | `minimal` | `summary` (default) | `full` |
|---|---|---|---|
| Claude `Bash`, Codex `Bash` | `Bash command` | Command after scrubbing, at most 300 chars; Approve omitted if longer | Command after scrubbing, at most 1,500 chars; Approve omitted if longer |
| Claude `Edit`/`Write`/`NotebookEdit` (opt-in) | `Edit 1 file` | Path relative to cwd, prefixed `BLIND WRITE:` | Same plus line counts. **Never file content or diff.** |
| Codex `apply_patch` (opt-in) | `Patch` | `BLIND WRITE:` then file paths parsed from `*** Update File:` / `*** Add File:` / `*** Delete File:` lines, at most 5, then `+N more` | Same |
| Claude `WebFetch` | `Fetch URL` | Hostname only | Full URL with query string scrubbed |
| MCP `mcp__server__tool` | `MCP tool` | `server / tool`; no arguments | Arguments as compact JSON after scrubbing, at most 300 chars |
| `ExitPlanMode`, `AskUserQuestion`, anything else | Not eligible; hook returns no decision | | |

**File approvals are blind.** For file tools the user sees which file, never what is written. That is why they are opt-in, and why the path denylist in section 4.3 exists. A path outside the project, or more than 5 paths in one patch, always goes to the terminal.

Rendering rules, applied before display and before length checks. **Nothing is silently deleted**; every change leaves a visible marker:

- A newline becomes ` ⏎ `, so `cmd1` followed by a newline and `rm -rf x` shows as `cmd1 ⏎ rm -rf x`, not as one fused line. Tabs become a single space.
- Every other control character (C0, DEL, C1), every bidi control (U+202A to U+202E, U+2066 to U+2069, U+200E, U+200F, U+061C) and every zero-width or invisible character (U+200B to U+200D, U+2060, U+FEFF, U+00AD) becomes a marker naming its code point, for example `[U+202E]`.
- Right-to-left letters (Hebrew, Arabic and the other bidi class R/AL scripts) become `[U+XXXX]` markers, and so does any non-ASCII character in the host of a `scheme://host` URL. Ordinary non-ASCII in paths and arguments (accented Latin, CJK) stays readable.
- Replace the home directory prefix with `~`.

Secret scrubbing, also applied before display. **It is a heuristic, not a guarantee:**

- Replace `NAME=value` where a whole segment of `NAME` (split on `_`, `-`, `.` and camelCase) names a secret (`key`, `token`, `secret`, `pass`, `password`, `pwd`, `auth`, `cred`, and compounds such as `PGPASSWORD`) with `NAME=[redacted N chars]`. `API_KEY` and `GH_TOKEN` match; `MONKEY` and `KEYBOARD` do not. **A value that holds shell syntax is never redacted**: `$(`, `${`, a backtick, a newline, `;`, `|`, `&`, `<` or `>` mean the value can run or chain something, so it is shown as it is. If a redaction ever did cover such syntax, Approve is withheld.
- Replace `Authorization:` / `Bearer` header values, credentials in URLs (`https://user:pass@`), and runs of 32 or more base64/hex characters with `[redacted N chars]`. A run that contains `/` or a backslash, or follows `~` or a backslash, is a path and is shown. A command far over the display budget has only its first 6,000 characters scrubbed (the rest is never shown), which bounds the work.
- Known misses: secrets passed as separate arguments (`--token abc123`, `--password hunter2`), glued short flags (`mysql -pSECRET`), short passwords anywhere, secrets in positional arguments, and any secret format the patterns do not know. Users who send real secrets through commands should use `minimal` display or keep the request topic on a server they run.

Redaction markers stay visible on purpose. A payload hidden in a long base64 blob shows up as `echo [redacted 812 chars] | base64 -d | sh`, which a user can recognise as suspicious (T11).

Never shown: file contents, diffs, environment, transcript text, the model-written `description` as the headline. Codex's `tool_input.description` ("human-readable approval reason, when Codex has one") may appear as a second line prefixed `Agent says:`.

Tension, stated plainly: minimal display leaks the least but means approving blind; full display lets the user judge but puts commands on the lock screen and, on public ntfy.sh, on third-party servers. `summary` is the compromise. Decisions D1 (public ntfy.sh) and D8 (`full` display) cover the public-server cases.

## 3. Hook contract per agent

### 3.1 Claude Code

Source: [hooks reference, PermissionRequest](https://code.claude.com/docs/en/hooks#permissionrequest) and [decision control](https://code.claude.com/docs/en/hooks#permissionrequest-decision-control), fetched 2026-10-08.

**When it fires.** "When Claude Code is about to ask you for permission to use a tool." Not for sandboxed network requests. For sessions hosted through the SDK `canUseTool` callback (Claude Desktop, VS Code), "the hooks run alongside your host, and whichever decides first applies."

**Input (stdin).** `tool_name`, `tool_input`, no `tool_use_id`, optional `mcp_server`, optional `permission_suggestions`:

```json
{
  "session_id": "abc123",
  "transcript_path": "/Users/.../00893aaf-19fa-41d2-8238-13269b9b3ca0.jsonl",
  "cwd": "/Users/...",
  "permission_mode": "default",
  "hook_event_name": "PermissionRequest",
  "tool_name": "Bash",
  "tool_input": { "command": "rm -rf node_modules", "description": "Remove node_modules directory" },
  "permission_suggestions": [
    { "type": "addRules", "rules": [{ "toolName": "Bash", "ruleContent": "rm -rf node_modules" }],
      "behavior": "allow", "destination": "localSettings" }
  ]
}
```

**Permission mode.** `permission_mode` is one of `default`, `plan`, `acceptEdits`, `auto`, `dontAsk`, `bypassPermissions` (hooks reference, fetched 2026-10-10). In `dontAsk` mode Claude Code "auto-denies every tool call that would otherwise prompt you", and `bypassPermissions` never prompts. The hook returns no decision in both, so a phone tap can never turn a policy denial into an allow.

**Entry point.** `src/approve.mjs` is a tiny wrapper that installs the exit-0-with-`{}` handlers and drops `NODE_TLS_REJECT_UNAUTHORIZED` before it loads the real logic (`src/approve-core.mjs`) with a dynamic `import()` inside a try/catch, so even a failure to load the logic prints `{}` and exits 0. The hook path in the agent settings is the wrapper and does not change.

**Output (stdout, exit 0).**

```json
{ "hookSpecificOutput": { "hookEventName": "PermissionRequest", "decision": { "behavior": "allow" } } }
```

```json
{ "hookSpecificOutput": { "hookEventName": "PermissionRequest",
  "decision": { "behavior": "deny", "message": "Denied from phone via anotifier." } } }
```

No decision: `{}`.

**Fields this design never sends.** `updatedInput` (the phone cannot edit, and it would be an injection vector), `interrupt`, and in v1 `updatedPermissions`.

**Documented semantics that matter.**

- A hook `allow` does not override a matching deny or ask rule; those "are still evaluated." The user's deny rules stay authoritative, which is a useful backstop.
- Exit code 2 is not honored for this event.
- Timeout default 600 s for command hooks; on timeout the output is discarded.
- `permission_suggestions` "isn't an exact list of the options you see" and can include `setMode` entries ([docs](https://code.claude.com/docs/en/hooks#permission-update-entries); also [#91216](https://github.com/anthropics/claude-code/issues/91216)). Never echo them back blindly. The prior art does exactly that for its "Always Approve" button.

**Unknown, must be verified empirically.**

|---|---|---|
| U1 | In the interactive terminal CLI, is the permission dialog shown **while** the hook runs, or only after it returns? | If it waits on the hook, a blocking hook freezes the local prompt (as Codex does, see 3.2). Docs only state concurrency for SDK hosts. |
| U2 | If the dialog is concurrent and the user answers at the terminal, is the hook process killed or left running? There is no "permission resolved" hook event ([#77700](https://github.com/anthropics/claude-code/issues/77700), [#79651](https://github.com/anthropics/claude-code/issues/79651)). | If left running, the phone notification stays live after the user already answered. |

Known gaps: decisions discarded in `--bg` sessions ([#88698](https://github.com/anthropics/claude-code/issues/88698)); not dispatched for agent-teams teammates ([#82418](https://github.com/anthropics/claude-code/issues/82418)); `ExitPlanMode` allow regressions ([#97656](https://github.com/anthropics/claude-code/issues/97656), [#90498](https://github.com/anthropics/claude-code/issues/90498)). | Each gap degrades to the terminal prompt, which is safe, but must be documented. |

### 3.2 Codex CLI

Sources: [Codex hooks docs, PermissionRequest](https://developers.openai.com/codex/hooks#permissionrequest), generated schemas [`permission-request.command.input.schema.json`](https://github.com/openai/codex/blob/main/codex-rs/hooks/schema/generated/permission-request.command.input.schema.json) and [`permission-request.command.output.schema.json`](https://github.com/openai/codex/blob/main/codex-rs/hooks/schema/generated/permission-request.command.output.schema.json), and [`permission_request.rs`](https://github.com/openai/codex/blob/main/codex-rs/hooks/src/events/permission_request.rs), all read on `main` on 2026-10-08. The docs warn that `main` schemas may include fields not yet released.

**When it fires.** "When Codex is about to ask for approval, such as a shell escalation or managed-network approval. ... It doesn't run for commands that don't need approval." The source states that this event "runs in the approval path, **before** guardian or user approval UI is shown." So **Codex does not show its approval prompt while our hook waits.** This is the main reason for away mode (section 4.1).

**Input.** Required: `cwd`, `hook_event_name` (`"PermissionRequest"`), `model`, `permission_mode` (`default|acceptEdits|plan|dontAsk|bypassPermissions`), `session_id`, `tool_input` (any JSON), `tool_name`, `transcript_path` (string or null), `turn_id`. Optional: `agent_id`, `agent_type`. `additionalProperties: false`. `tool_name` is `Bash`, `apply_patch` or `mcp__server__tool`; `Bash` and `apply_patch` carry `tool_input.command`; `tool_input.description` may be present.

**Output.** Same shape as Claude:

```json
{ "hookSpecificOutput": { "hookEventName": "PermissionRequest", "decision": { "behavior": "allow" } } }
```

```json
{ "hookSpecificOutput": { "hookEventName": "PermissionRequest",
  "decision": { "behavior": "deny", "message": "Denied from phone via anotifier." } } }
```

No decision: empty stdout or `{}` (exit 0).

**Documented semantics that matter.**

- `updatedInput`, `updatedPermissions` and `interrupt: true` are "reserved for future behavior and fail closed today." So Codex has **no hook-native "always allow"**.
- "If multiple matching hooks return decisions, any `deny` wins. Otherwise, an `allow` lets the request proceed." Source: "any deny wins, otherwise the last allow wins."
- Exit 2 with non-empty stderr is a deny; exit 2 without stderr is a failed hook. Other non-zero exits are failures with no decision.
- Plain non-JSON stdout is ignored; JSON that fails to parse as a permission-request output is a failed hook.
- Timeout default 600 s; a timeout is a failed hook with no decision.
- Non-managed hooks must be reviewed and trusted by hash in `/hooks` before they run ([docs](https://developers.openai.com/codex/hooks#review-and-trust-hooks)).
- Matching handlers run **concurrently**: the dispatcher pushes every handler into a `FuturesUnordered` and collects results with `pending.next().await` ([dispatcher.rs](https://github.com/openai/codex/blob/main/codex-rs/hooks/src/engine/dispatcher.rs)). So the existing notification hook on the same event (`setup/patch-config.mjs:13`) adds no latency to the approval hook. Caveat: this is read from `main`, which may be ahead of the pinned 0.144.0 (U7).

**Unknown, must be verified empirically.**

| ID | Question |
|---|---|
| U7 | Behavior on the pinned CI version (0.144.0), including handler concurrency. Exact release that introduced decision-returning `PermissionRequest` is unpinned. |

### 3.3 anotifier-side wiring

- Claude: a new `PermissionRequest` entry in `~/.claude/settings.json` with `matcher` set to the eligible tools (`Bash` by default; the user's opt-ins extend it, for example `Bash|Edit|Write|WebFetch`), command `node ".../src/approve.mjs" --source claude`, `timeout: waitSeconds + 30`, and `statusMessage: "Waiting for phone approval"`.
- Codex: a new `PermissionRequest` entry in `~/.codex/hooks.json` with the same pattern, `--source codex`, and **no pre-written trust hash** (T14, D6).
- While approval is engaged, `notify.mjs` skips its own `needs_input` push for Codex `PermissionRequest` and Claude `permission_prompt`, so the user does not get two pushes for one prompt. (Claude's `permission_prompt` notification fires only after about six seconds without typing, [docs](https://code.claude.com/docs/en/hooks#notification).)

## 4. UX

### 4.1 When the hook is allowed to block

Because Codex shows its approval prompt only after the hook returns, and Claude may do the same (U1), a hook that waits five minutes while the user sits at the keyboard is a regression. The design therefore engages remote approval only when the user says they are away:

```
anotifier away 2h      # engage until 2h from now
anotifier away off
```

This reuses the snooze state machinery (`cli/snooze.mjs`, `src/suppress.mjs`), with one deliberate difference in how a bad state file is read. Snooze treats a missing or corrupt state file as "not snoozed", because the safe outcome there is to notify. The away-state file (`~/.anotifier/approvals/away.json`) **fails closed**: missing, unreadable, corrupt, an expiry in the past, or an expiry implausibly far in the future (beyond the 24-hour maximum `anotifier away` accepts) all mean "not engaged", so the hook returns no decision and the terminal prompt appears. Engagement must never come from a broken file.

Away mode also limits the attack surface: the response channel can approve anything only while away mode is on. An `engage: "always"` setting exists for users who accept the blocked local prompt; setup explains the cost. If U1 shows Claude displays the dialog concurrently, Claude could engage always while Codex stays away-only.

Snooze and quiet hours turn approvals off too (the hook returns no decision), matching today's "silence every channel" rule in `src/notify.mjs`.

### 4.2 Opt-in setup

Off by default, never enabled by `anotifier setup`. A separate `anotifier approval setup`:

1. Explains in one screen that this lets the phone run commands on this machine.
2. Asks for the server. Offers self-hosted (prints the ACL recipe from 2.5 with the generated names filled in) or an ntfy.sh account with a reserved request topic. Anonymous public ntfy.sh is refused in v1 (D1). If a later version allows it, choosing it requires typing `public` to acknowledge, and forces `minimal` display and `X-Firebase: no`.
3. Generates topics, writes `approval.json` mode 0600, adds the hook entries.
4. Shows the request topic once as a QR code / subscribe link for the phone, then never prints it again in full (`status` shows `anr-****…last4`).
5. Sends a test request and requires the user to tap Approve on the phone. Setup does not finish until a real round trip works. This also proves the phone can reach the response URL.
6. Tells the user to hide sensitive content for the ntfy app on the lock screen, to turn off notification mirroring of the ntfy app to watches, and not to subscribe to the request topic in a desktop browser or the ntfy web app on a shared machine (T5).
7. Tells the user to treat any approval prompt they did not expect, or any button with an unusual label, as hostile and not to tap it (T10).
8. If the user opts in to file tools, states plainly: "File approvals are blind. Your phone shows the file name, not the change."

`anotifier approval rotate` regenerates both names. `anotifier approval off` removes the hook entries.

### 4.3 Per-tool eligibility list

`approval.tools` lists which tools may be decided from the phone. Default: `Bash` only, for both agents, because a command is the one request the phone can show in full. Opt-in: `Edit`, `Write`, `NotebookEdit` (Claude), `apply_patch` (Codex), `WebFetch`, `mcp__*`. File tools are opt-in because file approvals are blind (T16). Never eligible: `ExitPlanMode` (approving it exits plan mode and changes the session's permission mode, [hooks guide](https://code.claude.com/docs/en/hooks-guide)) and `AskUserQuestion`.

A tool that is not eligible gets no decision immediately, so the terminal prompt appears with no delay.

**Built-in path denylist (file tools).** Even when file tools are opted in, remote approval is never offered for a write to any of these; the hook returns no decision and the user answers at the terminal. Each is a place where a write becomes code execution later, outside any permission prompt:

| Location | Why |
|---|---|
| `.claude/settings.json`, `.claude/settings.local.json`, `~/.claude/settings.json`, anything under `.claude/` or `~/.claude/` (hooks, agents, commands, skills) | Claude Code hooks run arbitrary commands |
| `~/.codex/hooks.json`, `~/.codex/config.toml`, anything under a project `.codex/` | Codex hooks and config |
| `~/.anotifier/` | This feature's own config and hook state |
| `.git/hooks/*`, `.git/config` (`core.hooksPath`, `core.fsmonitor`) | Git runs them on ordinary git commands |
| `.husky/`, `.pre-commit-config.yaml`, `lefthook.yml` | Git hook managers |
| Shell startup files: `.bashrc`, `.bash_profile`, `.profile`, `.zshrc`, `.zprofile`, `.zshenv`, `config.fish`, PowerShell `profile.ps1` / `Microsoft.PowerShell_profile.ps1`, `.envrc` | Run on the next shell start or `cd` |
| `.github/workflows/`, `.gitlab-ci.yml`, `.circleci/` | CI runs them with repository secrets |
| `package.json` (scripts, lifecycle hooks), `.npmrc`, `.yarnrc.yml` | `npm install` / `npm test` run them |
| `.vscode/tasks.json`, `.vscode/settings.json` | Editors run tasks and tools from them |
| `~/.ssh/` | Credentials and `authorized_keys` |
| Any path outside the project (after resolving `..` and symlinks of the parent directory) | Not something the user scoped the session to |

Matching is on the normalised, resolved path, and case-insensitive on Windows and macOS. For `apply_patch`, every path in the patch is checked, and one hit sends the whole request to the terminal. The list is necessarily incomplete (`Makefile`, `setup.py` and build scripts also run code), which is the reason file tools stay opt-in and their approvals are labelled blind.

An optional `approval.neverRemote` list of command prefixes (`git push --force`, `rm -rf /`, `sudo`) also returns no decision. This is a convenience, not a security boundary: shell prefix matching is easy to evade.

anotifier does **not** keep its own allowlist of commands to auto-approve. Auto-approval belongs in the agent's own rules (`permissions.allow` in Claude Code, approval policy in Codex), where the agent enforces it and the user can see it.

### 4.4 "Always allow this session": analysis

What the button would do: approve this call and stop asking for similar calls for the rest of the session.

**Claude Code (native path exists).** Return `allow` with

```json
"updatedPermissions": [
  { "type": "addRules", "rules": [{ "toolName": "Bash", "ruleContent": "npm test" }],
    "behavior": "allow", "destination": "session" }
]
```

`destination: "session"` is in memory only and discarded when the session ends ([docs](https://code.claude.com/docs/en/hooks#permission-update-entries)). The agent enforces the rule and it is visible in `/permissions`.

**Codex (no native path).** `updatedPermissions` fails closed. The only way is for anotifier to remember the grant and auto-allow later requests itself. Then anotifier becomes an auto-approver the agent does not know about, and a single forged or mistaken tap becomes a standing grant. **Do not build this.**

**Risks, even on Claude:**

1. **Amplification.** One tap, possibly from a lock screen (U6) or by an attacker reading the request topic (T1), becomes a standing capability for the session instead of one command.
2. **Rule scope is invisible on a phone.** Claude's own suggestions can be broad (prefix rules, `setMode: acceptEdits`, `localSettings` persistence). The prior art applies `permission_suggestions` verbatim, so its "Always Approve" can persist rules to disk or switch the session mode.
3. **Prompt-injection leverage.** A model that gets one benign command "always" approved can sometimes reuse the rule with different arguments, depending on how the rule matches.
4. **Fat-finger risk.** Three buttons side by side on a notification.

**Recommendation.** Not in v1. If added later: Claude only; behind `approval.allowSessionRules: true`; build the rule ourselves (never from `permission_suggestions`); exact `ruleContent` only (no wildcards); `destination: "session"` only; never `setMode`, `addDirectories` or any persistent destination; label the button with the exact rule (`Always: Bash(npm test)`); send a receipt naming the rule.

## 5. Test plan

### 5.1 Unit (all OS, `unit.yml`)

- Name and token generation: lengths, alphabet within `[-_A-Za-z0-9]`, `randomBytes` used (inject the RNG, as `generateTopic` does today).
- Response parser table. Stream-level cases come first: `open` and `keepalive` events are skipped, and only `event === "message"` is considered, with the response JSON read from its `message` field. A `message` event whose `message` field is not JSON is ignored. Then the body cases: valid allow, valid deny, wrong `rid`, wrong token, allow body carrying the deny token, token of the wrong length, `v` missing, oversized body, non-JSON, duplicate after first valid, arrival after `expiresAt`.
- Output golden files per agent: exact allow, deny and no-decision bytes for Claude and Codex, validated against the Codex output schema.
- Display renderer: newline shown as `⏎` (two commands never fuse), control, bidi and zero-width characters shown as `[U+XXXX]` markers and never dropped, scrubbing rules plus a table of the documented misses (`--token abc`, `-pSECRET`) that asserts they are **not** caught, so the docs stay honest, truncation that removes the Approve action, `apply_patch` path extraction, and the `BLIND WRITE:` label.
- Path denylist: every entry in the 4.3 table, `..` traversal, symlinked parent directory, case variants on Windows and macOS, and a patch with one denylisted path among clean ones.
- Pending slots: 5 live slots means the 6th request gets no decision; a stale slot (dead PID or past expiry) is reclaimed; the slot is freed on every exit path; an unwritable directory gives no decision.
- Away state: missing, corrupt, past expiry, and far-future expiry all read as "not engaged".
- Gate order: disabled, not away, snoozed, ineligible tool, denylisted path, no free slot, `http://` server: each returns `{}` without network.
- `doctor` `approval-token`: warns 14 days before the recorded expiry and fails after it.

### 5.2 Fault injection (the safety property)

A harness runs `approve.mjs` as a subprocess with a fake server that fails at each step (connect refused, TLS error, 429, 500, slow headers, stream cut mid-message, malformed JSON, 10 MB stream, SIGTERM at a random time, unreadable `approval.json`, malformed stdin). **Invariant: stdout is `{}` and exit code is 0 in every case without a valid token.** The only case allowed to print `allow` is a correct token before expiry. This test guards against T13 and must run on every PR that touches `src/approve*.mjs`.

### 5.3 Real ntfy server (new lane, `ubuntu-latest`)

ntfy server runs on Linux and Windows but not macOS ([install docs](https://docs.ntfy.sh/install/)). Download a pinned Linux release binary, start it with the exact ACL recipe from 2.5, and assert:

- anonymous read of the request topic is denied; anonymous read of a response topic is denied; anonymous write to a response topic works; the agent token can publish and subscribe as designed;
- a **phone simulator** (`scripts/approval/phone-sim.mjs`) logs in as `phone`, subscribes to the request topic, parses `actions`, and performs the chosen `http` action exactly as the ntfy app would (method, URL, headers, body);
- full loop: approve, deny, timeout, wrong token, replay of a previous response body against a new request, two concurrent requests answered in reverse order.

| F4a to F4d Claude | Same four with `claude` and a Bash tool call | Same assertions. F4c also records whether the dialog was visible during the wait, which answers **U1**; F4e answers at the terminal mid-wait and records U2 and U3 |

These spend real API credits, like F1 and F2. Run them on PRs that touch `src/approve*.mjs` or the hook wiring, and on `main`. `tui-proofs.yml` already ignores `docs/**`, so this design PR triggers no paid CI.

### 5.5 Live ntfy.sh lane

Weekly scheduled run of F3a against public ntfy.sh, to catch server behavior changes. Kept weekly because ntfy.sh's 250 messages per day per IP has already broken E2E runs here.

### 5.6 Manual device checklist (cannot be automated in CI)

On a real Android phone and a real iPhone with the ntfy app, plus a Wear OS watch, an Apple Watch, a desktop browser with ntfy web push, and the ntfy web app:

1. Buttons render; Approve and Deny each work.
2. **U6, phone:** with the phone locked, can Approve be tapped without unlocking? Test with "hide sensitive content" on and off.
3. **U6, watch:** does the notification mirror to a Wear OS watch and an Apple Watch with its buttons, and can Approve be tapped on the watch while the phone is locked?
4. **U6, desktop and web:** does a browser desktop notification show the buttons, and does the ntfy web app fire the `http` action? Does either need anything beyond an unlocked desktop session?
5. `clear: true` dismisses the notification after a successful POST (Android).
6. The expiry update replaces the notification on Android and web; on iOS a second notification appears (expected, since update/clear is Android and web only).
7. With `X-Firebase: no`, does Android still deliver promptly? Does iOS deliver at all?
8. Lock-screen and watch preview content in each display mode.

An Android emulator lane could automate 1, 5 and 6 later; not proposed for v1.

## 6. Open questions for the maintainer

1. **Away mode vs. always-on.** Is requiring `anotifier away` acceptable UX, or is the expected product "phone and terminal race, first answer wins"? The second is only possible on Claude, and only if U1 shows the dialog is concurrent.
2. **Public ntfy.sh.** This design says not in v1 (D1). Is that acceptable for the zero-infra users who are the product's niche, or should the acknowledged-and-minimal alternative ship?
3. **Separate request topic vs. reusing the notification topic.** This design says separate (another phone subscription for the user). Acceptable?
4. **Should anotifier offer a hosted ntfy instance** (for example under anotifier.io) with ACLs? That makes Devino the trusted operator of a command-execution channel for users, with the liability that implies. This design assumes no.
5. **Away-mode auto-off.** Turn away off automatically when the user next types in the terminal? Hooks cannot see keystrokes, but `UserPromptSubmit` (Claude) proves presence. Worth wiring?
6. **Telemetry.** Count approvals (allowed / denied / expired / no-decision reason) in the opt-in usage summary? Never content, never topics.
7. **Windows file permissions.** Use `icacls` to restrict `approval.json` to the user, or rely on the default profile ACL?
8. **Fix the existing config file mode** (`src/config-loader.mjs:250`) now, independently of this feature? The notification topic and webhook URLs are already secrets.

## 7. Decision needed

| ID | Decision | Recommendation |
|---|---|---|
| D1 | Allow anonymous public ntfy.sh for remote approval? | **Not supported in v1.** Its security rests on a topic name never leaking, the operator and push relays see every token, and anyone holding the topic can push buttons that fire arbitrary requests from the phone (T10). Self-hosted with ACLs, or an ntfy.sh account with a reserved request topic, are the supported setups. Documented alternative if the maintainer wants the zero-infra path: allow it behind an explicit acknowledgement, with `minimal` display and `X-Firebase: no` both required, not merely defaulted. |
| D2 | Any failure mode that returns `allow`? | **No. Should not ship in any form.** Timeout, error, malformed reply and quota exhaustion all return no decision. |
| D3 | Ship "always allow this session" in v1? | **No.** Revisit for Claude only, with the constraints in 4.4. **Never** apply `permission_suggestions` verbatim; that should not ship. **Never** build an anotifier-side auto-allow memory for Codex; that should not ship. |
| D4 | Ship before U6 (action without unlock, on phone, watch, desktop or web) is answered? | **No.** If any of those surfaces fires `http` actions without device authentication, document it prominently and require the user to acknowledge it at setup, or do not ship. |
| D5 | Engage without away mode? | Away-only for Codex (verified: the prompt waits on the hook). For Claude, decide after U1. |
| D6 | Pre-write the Codex trust hash for the approval hook as setup does for notification hooks? | **No.** The user should review a hook that can approve commands in `/hooks` once. Silently trusting it defeats Codex's review gate. |
| D7 | Implement inside `notify.mjs` behind a flag, or a separate `approve.mjs`? | **Separate entry point.** Keeps `notify.mjs`'s never-block contract intact, and gives Codex a distinct hook definition to review (T14). |
| D8 | Display `full` mode for Bash on public ntfy.sh? | Allow only on self-hosted or authenticated servers. |
| D9 | Exact wait default | 300 s with hook `timeout` 330 s. Lower if users report blocked sessions. |
| D10 | Make file tools (Edit, Write, NotebookEdit, apply_patch) eligible by default? | **No.** File approvals are blind. Opt-in only, always with the built-in path denylist (4.3), which cannot be turned off. |

## Non-goals

- Cursor (`beforeShellExecution` and related hooks) and Gemini CLI (`BeforeTool`). Neither contract was verified for this document.
- Answering `AskUserQuestion` from the phone (the prior art does this; it is input injection rather than approval, and deserves its own design).
- Editing the command on the phone (`updatedInput`).
- A custom phone app or web page that could hold a key and sign responses. That would allow real phone-side HMAC, but it breaks the zero-infra posture.
